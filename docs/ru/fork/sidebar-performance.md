# Быстрые большие списки проектов

> Раздел реестра §21. Часть [реестра правок форка](../fork-changes.md).

## §21 Виртуализация проектов

- **Слой:** frontend · **Столкновение:** 🟡 (две точки в общих sidebar-компонентах)
  · **PR:** кандидат, не открыт.
- При каждом переключении Projects ↔ Conversations большой список монтировался
  заново. На наборе из 513 проектов он создавал 13–15 тысяч DOM-элементов;
  разметка/React блокировали основной поток даже при мгновенном ответе API.
- Для списков больше 60 проектов используется `react-virtuoso` 4.18.20:
  монтируется только видимое окно с запасом 200px. Высоты раскрытых проектов
  библиотека измеряет автоматически; используется тот же внутренний scroll-root
  `ScrollArea`, без второго скролла. До привязки root большой список не
  монтируется полностью даже на один кадр.
- Маленькие списки и standalone-компонент без scroll-root остаются обычными.
  Строки и их меню не переписаны: исходные данные, сортировка, избранное,
  раскрытие, переименование, выделение сеансов и серверная пагинация прежние.
  Ключ строки — `projectId`, не индекс. Поиск работает по всем проектам, а не
  только по смонтированным строкам. Сами диалоги не удаляются и не архивируются.
- **Файлы:** `src/modules/sidebar/{SidebarContent,SidebarProjectList}.tsx`,
  `src/modules/sidebar/tests/sidebarRowProps.test.tsx`, `package.json` и lock.
- **Мерж:** сохранить общий scroll-root и виртуализацию, но брать исправления
  upstream в `SidebarProjectItem`/`SidebarProjectSessions`. Не заменять
  постраничные данные обрезанной выборкой первых проектов.

## Что измерено 2026-11-08

Рабочая SQLite проверялась только на чтение: 6,8 MiB, 2412 сеансов, 513 проектов,
3 свободных страницы. Стандартные запросы списка с запуском sqlite CLI —
4–30 мс; на отдельной копии БД `listRecentSessions` — 10–11 мс,
`getProjectsWithSessions({skipSynchronization:true})` — 110–130 мс. Эти числа
не измеряют полный первоначальный обход transcript-файлов. Оснований удалять
историю или запускать VACUUM ради секундного ожидания не найдено.

На ноутбуке были заняты около 6,8 GiB swap и наблюдался swap I/O, при этом CPU в
момент замеров в основном простаивал. Это может усиливать рывки, но отдельная
ошибка большого рендера воспроизведена без чтения рабочей БД из браузера.

Chrome/Playwright, production-сборка, синтетические имена/пути/тексты той же
длины и та же структура данных: 513 проектов, 296 сессий в первых страницах,
522 разговора; API списков подставлен локально.

| Замер | До | После |
|---|---|---|
| DOM, Projects, mobile | 14 718 элементов | около 777 |
| Возврат в Projects, 390×844 | 349–403 мс | 134–140 мс |
| Возврат в Projects, mobile + CPU 4× | 1152–1742 мс | 195–258 мс |
| Максимальный long task при этом | 1477 мс | 0 задач дольше 50 мс в трёх переходах |
| Возврат в Projects, 1280×800 | 281–320 мс | 97–98 мс |

CPU 4× — искусственное замедление для сравнения, не замер реального телефона и
не обещание конкретного времени по сети. Переключение в Conversations и
раскрытие проектов также ускорились; серверные запросы не отключались и кэш
со старой историей не добавлялся.

## Проверки

- 4 регрессии на границу виртуализации, отсутствие полного первого кадра,
  стабильные ключи/полный набор данных, поиск несмонтированного проекта,
  раскрытие, переименование и выделение.
- Полный клиентский набор: 164 файла, 1240 тестов успешно с `NODE_ENV=test` и
  `--maxWorkers=4`. Первый параллельный прогон дал один нестабильный auth-тест;
  адресный повтор и полный прогон с четырьмя workers успешны, auth-код не менялся.
- Typecheck, lint и клиентская сборка успешны, новых lint-предупреждений нет.
- В браузере проверены повторные переходы, раскрытие групп, поиск 513-го
  проекта и прокрутка до него — на 390×844 touch и 1280×800. Скриншоты просмотрены.
