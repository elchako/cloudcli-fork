# Навигатор по вопросам пользователя

> Раздел реестра §17. Часть [реестра правок форка](../fork-changes.md): номер § — постоянный адрес правки, по нему на эту страницу ссылаются код и коммиты.

- **Слой:** frontend + server · **Столкновение:** 🟢 (почти всё — новые файлы)
  + 🟡 (несколько строк в общих файлах, список ниже) · **PR:** кандидат —
  оглавление по своим вопросам полезно не только нам.
- **Зачем (26.10.2026):** в длинном сеансе теряется нить: о чём спрашивал, с
  чего начинал. Справа в ленте нужно оглавление только по вопросам
  пользователя, без ответов ИИ.
- **Как выглядит:**
  - мышь: столбик коротких полосок, по одной на вопрос; текущая ярче и шире.
    При наведении полоски расширяются, у наведённой — подсказка с текстом
    вопроса. Клик — переход к вопросу. Шевроны ↑/↓ — предыдущий и следующий:
    ↑ из середины ответа сначала возвращает к началу текущего вопроса.
    Точки сверху и снизу — не всё влезло, столбик прокручивается колесом.
    Колесо над столбиком, когда прокручивать нечего, листает ленту;
  - тач: в полоску 10 px пальцем не попасть, поэтому тап по столбику
    открывает список вопросов (номер + две строки текста) во всю высоту
    ленты. Тап по пункту — переход. Мышь это или палец, решает `pointerType`
    самого нажатия, а не медиазапрос: гибридные устройства на `(hover:)`
    отвечают как попало;
  - слэш-команды (`/compact`, `/skill …`) входят в список, их полоска
    бледнее; вопросов меньше двух — столбика нет.
- **Почему нужен сервер.** Клиент грузит историю страницами по 20 записей, и
  в сеансе с инструментами на странице обычно один вопрос или ни одного:
  оглавление по загруженному было бы пустым. Новый
  `GET /api/providers/sessions/:sessionId/prompts` отдаёт только вопросы:
  `{ key, anchorId?, timestamp, fromEnd, text, attachmentCount, isCommand }`
  и `total`. Источник — тот же `sessionsService.fetchHistory` (для
  Claude/Codex — тёплый `sessionHistoryCache`). На живых данных: сеанс 29 МБ
  с 41 вопросом — 17 КБ ответа, около 280 мс на холодный разбор.
  - вопрос = user-строка, которую лента рисует пузырём: без
    `parentToolUseId` и не `<task-notification>`. `<system-reminder>` и
    `<ide_*>` внутри текста вырезаются; пустое без вложений — пропускается;
  - соседние user-строки с одним временем — это части одного хода (Claude
    дробит текст, OpenCode пишет строку на часть) и склеиваются;
  - `key` — uuid строки Claude (`transcriptAnchorId`), иначе timestamp
    (у Codex anchor есть не у всех вопросов, id генерируются на каждое
    чтение);
  - `fromEnd` — сколько записей от конца истории до вопроса: это `limit`
    хвостовой страницы, в которой он есть;
  - **Cursor — пустой список.** Его история штампует время
    `Date.now() + n×100 мс` при каждом чтении, ни ключ, ни позиция не
    совпадут с загруженным. Клиент тогда показывает только загруженные вопросы.
- **Слияние на клиенте** (`mergePrompts`): серверный список главный. Из
  загруженных строк добавляются только вопросы новее последнего в списке
  (только что отправленный). Оптимистичное эхо без anchor, у которого часы
  телефона ушли вперёд, гасится парой «один к одному» с тем же текстом
  в окне [−10 с, +5 мин], как в `sessionMessageReconciliation.ts`. Правило
  «серверные старше первой загруженной строки» отвергнуто: стор держит вечные
  realtime-строки (ошибки, несовпавшее эхо), и граница по `chatMessages[0]`
  теряет вопросы. Список перечитывается при смене сеанса и при изменении
  `slot.total` в простое (конец рана, правка, подгрузка); во время рана — нет.
- **Текущий вопрос:** на прокрутке (rAF) берутся строки ленты — внуки
  контейнера, без `querySelectorAll` по всему DOM — и ищется последний
  вопрос выше «линии чтения» (30 % высоты, не выше шапки). Нет отрисованного
  вопроса выше линии — читатель в ходе предыдущего, незагруженного. У самого
  низа короткий последний ход до линии не поднимется, поэтому там текущим
  становится последний вопрос, видимый на экране. После перехода вопрос
  закреплён текущим, пока пользователь сам не прокрутит (wheel, touch,
  pointerdown, клавиши).
- **Переход** (`usePromptNavigator.jumpTo`):
  1. вопрос загружен — найти строку по anchor, иначе по timestamp и типу user;
  2. не загружен — `sessionStore.fetchFromServer(limit = fromEnd + записи,
     дописанные после чтения списка, + 20, offset 0)`: только хвост до вопроса,
     а не вся история (поиск из сайдбара тянет всю). Промах (историю
     переписали) — `limit: null`;
  3. `revealRowAt` расширяет окно отрисовки до строки и гасит начальный
     цикл «прилипания к низу» открытого сеанса. Это единственная правка в
     `useChatSessionState.ts`: флаг `searchScrollActiveRef` поиска **не**
     используется, при сбое прыжка он навсегда выключил бы автоскролл;
  4. 2 с покадрово (rAF) держать верх строки под липкой шапкой (экспорт,
     фоновые задачи): вокруг монтируются ленивые строки, догружаются
     картинки, в Safari нет scroll anchoring. Ввод пользователя
     выравнивание прерывает. Пузырь вопроса коротко обводится (Web
     Animations, без правок CSS).
- **Размещение:** поверх ленты, в обёртке `relative` вокруг
  `ChatMessagesPane`. Отступ справа = ширина скроллбара + 4 px, сверху —
  под липкую шапку. **Ручка быстрых настроек** приколота к тому же краю на
  высоте, которую пользователь перетаскивает. Если она в зоне столбика,
  столбик уходит в бо́льшую свободную часть: выше или ниже ручки. Ручку
  находим по `data-quick-settings-handle`. Пересчёт идёт по `ResizeObserver`
  на ленте (открылась закреплённая панель) и по `mouseup`/`touchend` (ручку
  отпустили).
- **Файлы:**
  - новые: `server/modules/providers/services/session-prompts.service.ts`,
    `src/modules/chat/utils/promptNavigator.ts` (чистые функции),
    `src/modules/chat/hooks/usePromptNavigator.ts`,
    `src/modules/chat/transcript/ChatPromptNavigator.tsx`, тесты
    `server/modules/providers/tests/session-prompts.service.test.ts`,
    `src/modules/chat/tests/promptNavigator.test.ts`,
    `src/modules/chat/tests/chatPromptNavigator.test.tsx`;
  - общие (🟡): `provider.routes.ts` — маршрут `/prompts` и импорт;
    `src/shared/api.ts` — `api.providers.sessionPrompts`;
    `useChatSessionState.ts` — `revealRowAt` и его возврат;
    `ChatInterface.tsx` — вызов хука, обёртка `relative` и навигатор.
    Строки `<ChatMessagesPane …>` **намеренно не переотступлены** внутри
    новой обёртки, чтобы не задеть их при мерже;
    `QuickSettingsHandle.tsx` — атрибут `data-quick-settings-handle`;
    `locales/{en,ru}/chat.json` — блок `promptNavigator` (остальные языки
    берут английский через `fallbackLng`).
- **Архитектуру разбирал скептик** (отдельный агент по коду). Принято из его
  разбора: серверный список главный, Cursor без серверного списка, `fromEnd`
  вместо индекса от начала, склейка частей хода, эхо один к одному, без
  `searchScrollActiveRef`, гашение начального скролла, отступ под шапку,
  долгое выравнивание с отменой вводом, `pointerType`, высота в процентах
  ленты, а не `vh`, обход скроллбара, проброс колеса.
- **Тесты:** сервер — 5 (фильтр, склейка, вырезка контекста, `fromEnd` и
  ключи на настоящем Claude-транскрипте, Cursor); клиент — 15 на чистые
  функции (сбор, слияние, эхо, поиск строки, текущий вопрос) и 6 на
  компонент (клик мышью, тап, подсказка, шевроны, колесо, скрытие при одном
  вопросе). Полные прогоны: vitest 116 файлов / 807 тестов; сервер
  (изолированный env) 821, 0 падений, 1 пропуск (как у апстрима).
  typecheck чистый, oxlint — 136 предупреждений, как в эталоне.
- **Проверено вживую:** тестовый инстанс (`env -i`, свой `HOME` с копиями
  двух настоящих транскриптов, своя БД, порт 3411, Vite 5181), 1280×800 и
  390×844, светлая и тёмная тема. 41 полоска при одном загруженном вопросе;
  подсказка при наведении; переход к незагруженному вопросу встаёт под
  шапку; ↑/↓ и ↑ из середины хода; текущий вопрос следует за ручной
  прокруткой; столбик обходит ручку настроек; на телефоне тап открывает
  список, тап по пункту — переход и закрытие.
- **Известные ограничения:**
  - **переход к самому первому вопросу длинного сеанса тянет всю историю
    до него.** Сеанс 29 МБ — 10,4 МБ JSON, локально 0,43 с; по мобильному
    Tailscale это секунды. Пока грузится, столбик пульсирует, прокрутка
    отменяет переход. Сжатия ответов на сервере нет — кандидат в отдельную
    правку (`compression` для `/api`);
  - после перехода к старому вопросу окно отрисовки не сужается обратно (как
    и после поиска и прокрутки вверх). Сужение — кандидат на доработку;
  - после правки сообщения вырезанные вопросы видны в столбике до конца
    нового рана, когда список перечитывается. Переход к такому вопросу
    просто ничего не делает.
- **Мерж-заметка:** если апстрим сделает своё оглавление — сравнить и
  перейти на его, наши файлы снять. Следить за структурой ленты
  `лента › список › обёртка строки` (`readRenderedRows`) и атрибутом
  `data-message-timestamp` на обёртке `LazyMessageRow`: без них текущий
  вопрос не определится (переход продолжит работать через
  `querySelector`).
