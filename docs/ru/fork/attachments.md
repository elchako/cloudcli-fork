# Вложения: любые файлы и сохранность при смене чата

> Разделы реестра §2.2, §18.2, §19.1. Часть [реестра правок форка](../fork-changes.md): номер § — постоянный адрес правки, по нему на эту страницу ссылаются код и коммиты.

## §2.2 Прикрепление любых файлов (не только картинок)

- **Слой:** frontend + server · **Столкновение:** 🟡 · **PR:** кандидат.
- **Что:** к сообщению можно прикрепить любой файл; не-картинки доходят до агента
  как читаемый путь (блок `<files_input>`), а не base64. Проверка типа и лимита
  (20 МБ / 5 файлов) с уведомлением о превышении.
- **Файлы:** `src/components/chat/utils/attachmentSupport.ts`,
  `src/components/chat/hooks/useChatComposerState.ts`,
  `server/shared/image-attachments.ts`,
  `server/modules/assets/services/image-assets.service.ts`,
  `server/modules/assets/assets.routes.ts` (форс-download не-картинок).
- **Trust boundary:** файл доходит до агента только если лежит в
  `~/.cloudcli/assets` или в cwd рана (`isAllowedImageSourcePath`). Не ослаблять.
- **Мерж-заметка (v1.37.0):** upstream ввёл свой `ComposerAttachment` (картинки +
  файловые плашки + зум/lightbox) — он поглотил наш прежний `ImageAttachment.tsx`
  (удалён). Наша логика допуска/лимита осталась в `useChatComposerState`.

## §18.2 Дополнительный фикс: вложения не теряются при смене чата

- **Слой:** frontend · **Столкновение:** 🟡 (`useChatComposerState.ts`) ·
  **PR:** кандидат в upstream; баг воспроизводится в новой очереди и общей
  асинхронной отправке, не зависит от наших моделей.
- Скептик указал на отказ enqueue после A→B: код восстанавливал лишь текст,
  а файлы терялись. Тесты подтвердили потерю файлов и попадание файлов A в B,
  если переключиться во время upload. Вложения в памяти композера теперь
  хранятся по существующему `draftScope`; серверный append остаётся источником
  истины, формат persistence не меняется.
- Повторный проход скептика нашёл пропущенную прямую отправку: её поздняя
  очистка могла стереть новый текст/файлы B и оставить отправленный File в A.
  Исправлено: `submissionScope` захватывается до первого await, из A удаляется
  только отправленный снимок файлов, текст очищается лишь при совпадении со
  снимком; новый ввод A/B не затрагивается. Ошибка upload ничего не очищает.
- **Контроль до/после:** 3 первоначальных regression failures, затем 3 на
  прямой отправке и ещё 1 на A→B→A во время queue-upload воспроизведены до
  соответствующих исправлений. После — 54 профильных теста проходят, в том
  числе 38 в `composerQueuedFollowUps.test.ts`; 8 вариантов прямой отправки
  покрывают успех/ошибку × новый черновик A × возврат до/после upload.
  Третий узкий проход скептика подтвердил закрытие P1; новых подтверждённых
  дефектов в этих ветках не найдено.
- Новый upstream-тест `chatInterfaceScheduledMessagesSubscribe.test.tsx`
  изолирует навигатор форка отдельными mocks, как и остальные не относящиеся
  к расписанию части ChatInterface: без этого его неполный sessionStore
  вызывал `getSessionSlot is not a function`. Сам навигатор по-прежнему
  проверяется своими тестами и живой браузерной приёмкой.
- Ограничение не меняется: принятая очередь хранит дескрипторы, а ещё не
  отправленные File — только память композера, не перезагрузка страницы.
  Пользовательское описание — [`chat.md`](../chat.md).

## §19.1 Steering сохраняет черновики и не дублирует вложения

- **Слой:** frontend · **Столкновение:** 🟡 (`useChatComposerState.ts`) ·
  **PR:** кандидат; не открыт.
- При слиянии v1.37.8 очередь получила `fromComposer: false` для отказанного
  steer. Сохранён наш `setScopeAttachedFiles`: восстановление не дублируется
  дополнительным upstream `setAttachedFiles`, а новая очередь не очищает текст,
  введённый после снимка отправки.
- Новая `steerIntoRunningTurn` подчиняется той же границе, что прямая отправка:
  забирает только отправленные файлы исходной сессии, очищает текст только при
  совпадении со снимком. Это работает и после A→B→A во время upload.
- **Файлы:** `src/modules/chat/hooks/useChatComposerState.ts`,
  `src/modules/chat/tests/composerQueuedFollowUps.test.ts`.
- **Регрессии:** steer с обычным файлом после переключения A→B, возвратом до/после
  загрузки и новым вводом; отказ steer и очереди со смешанными вложениями
  возвращает исходные файлы один раз. Прежние проверки очереди и прямой отправки
  также проходят. Серверный формат вложений и trust boundary не расширены.
