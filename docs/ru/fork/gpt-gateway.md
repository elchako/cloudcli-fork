# GPT через шлюз CLIProxyAPI: effort и окно контекста

> Разделы реестра §1.3, §1.3-бис, §16.2. Часть [реестра правок форка](../fork-changes.md): номер § — постоянный адрес правки, по нему на эту страницу ссылаются код и коммиты.

## §1.3 GPT-6 Astra и GPT-6.1 Sol через шлюз CLIProxyAPI

- **Слой:** модель + server · **Столкновение:** 🟡 (тот же массив моделей +
  строка в `mapCliOptionsToSDK`) · **PR:** нет (специфично для шлюза холдинга).
- **Что:** в каталог Claude добавлены `gpt-6-astra` и `gpt-6.1-sol` (подписка
  ChatGPT в CLIProxyAPI, тот же `ANTHROPIC_BASE_URL`). Модели ходят через тот же
  Claude CLI: шлюз переводит Anthropic `/v1/messages` в Codex и обратно —
  инструменты, стриминг и транскрипт работают как с Claude (проверено живым
  прогоном: Bash/Read, многоходовые сессии).
- **Effort через суффикс модели.** Шлюз **игнорирует** `output_config.effort`
  для GPT (замер: low и max давали одинаковый расход reasoning; мусорное
  `ultra` принималось без ошибки), зато понимает суффикс `модель(уровень)`:
  `gpt-6-astra(max)` ≈ в 1,7 раза больше reasoning-токенов, чем `(low)`, а в
  ответе и транскрипте остаётся чистое `gpt-6-astra`. Поэтому
  `withGatewayEffortSuffix` (в `claude-models.provider.ts`) дописывает выбранный
  уровень к id модели прямо перед SDK; в БД и UI модель остаётся без суффикса.
  Уровни — ровно те, что шлюз сам называет допустимыми для GPT-6:
  `low/medium/high/xhigh/max`. «Default» в меню = без суффикса = уровень шлюза.
- **Контекст:** окно задано через `CLAUDE_CODE_MAX_CONTEXT_TOKENS` (930k) —
  см. §1.3-бис. `[1m]` к id по-прежнему не ставим: суффикс ушёл бы в шлюз как
  часть имени модели, и CLIProxyAPI её не узнал бы.
- **Файлы:** `server/modules/providers/list/claude/claude-models.provider.ts`
  (`GATEWAY_GPT_EFFORT`, записи моделей, `withGatewayEffortSuffix`,
  обратная `withoutGatewayEffortSuffix`),
  `server/modules/providers/list/claude/claude-runtime.provider.ts`
  (`mapCliOptionsToSDK`; с v1.37.5 ещё сопоставление окна контекста в
  `readReportedContextWindow`, §16.2); тесты
  `server/modules/providers/tests/claude-models.test.ts`, последний тест в
  `claude-context-window.test.ts`.
- **С §22.2:** тот же транспорт применяется к подтверждённым Gemini/Claude
  Antigravity и моделям с явным `effort.transport=model-suffix` из API.
  Источник уровней — реальные metadata registry, не Codex-client шаблоны;
  нативный Claude не получает suffix ([§22.2](api-models.md)). При мерже
  проверить валидацию модели/уровня до suffix и сопоставление окна контекста.

## §1.3-бис Окно контекста GPT шлюза — 930k через CLAUDE_CODE_MAX_CONTEXT_TOKENS

- **Слой:** эксплуатационная настройка, **не доработка кода** ·
  **Столкновение:** 🟢 (нет правок `src/`/`server/`) · **PR:** нет.
- **Симптом:** авто-сжатие сессий GPT начиналось на ~200k токенов. Сжимает не
  CloudCLI и не шлюз, а сам Claude CLI: для id, который он не знает, он считает
  окно равным дефолту нераспознанной модели — 200 000 (константа в бинаре
  v2.1.280) — и держит сессию в этих пределах. Шлюз в `/v1/models` окно не
  сообщает, узнать его самостоятельно CLI не может.
- **Что сделано:** 11.10.2026 добавлен drop-in службы
  `~/.config/systemd/user/cloudcli-fork.service.d/context-tokens.conf` с
  `Environment=CLAUDE_CODE_MAX_CONTEXT_TOKENS=1000000` (31.10.2026 снижено до
  `930000`, см. ниже). Рантайм пробрасывает
  весь `process.env` в субпроцесс CLI (`mapCliOptionsToSDK`,
  `claude-runtime.provider.ts`), поэтому переменная видна каждому рану. Гейт
  внутри CLI применяет её только к моделям, которые он не знает (канонические
  `claude-*` пропускает), — Claude с `[1m]` и kimi-k3[1m] она не меняет.
- **Было 1 000 000, с 31.10.2026 — 930 000.** Расчёт исходил из окна
  GPT-6.1 Sol 1 050 000 (вход+выход) с запасом 50k, но шлюз отказывает
  раньше. Порог авто-сжатия в CLI 2.1.314 = окно − min(max output, 20 000) −
  13 000; при 1M это 967k (Claude-сессии в журналах и правда сжимаются на
  966–974k). GPT-6.1 Sol же в журналах сессий 25–26.10.2026 прошёл с 929 065
  токенами входа, а следующий запрос (~931–937k, `max_tokens` 32000) получил
  `400 Your input exceeds the context window of this model`. Сжатие на 967k не
  успевало, сессия упиралась в ошибку и её сжимали вручную через `/compact`.
  При 930 000 сжатие срабатывает на ~897k; запас ~33k покрывает крупный шаг
  (Read до 25k токенов), после которого запрос на сжатие ещё помещается в
  лимит. 950 000 дало бы порог 917k с запасом всего ~13k. Для gpt-6-astra
  отдельного замера нет — значение общее для всех нераспознанных моделей.
- **Запасные ручки (не используются):** `CLAUDE_CODE_AUTO_COMPACT_WINDOW`
  (порог именно авто-сжатия, приоритетнее расчётного) и
  `CLAUDE_CODE_DISABLE_UNKNOWN_MODEL_WINDOW_ENFORCEMENT=1` (не навязывать
  потолок, ждать ошибку API).
- **Проверка после рестарта службы:** новая GPT-сессия не должна показывать
  предупреждение unknown-model, счётчик контекста показывает знаменатель
  930k, авто-сжатие (`compact_boundary`, `trigger: auto`) — на ~897k.
- **С v1.37.5 счётчик контекста в композере берёт окно у CLI.** Апстрим
  (#1557) берёт итог окна из `result.modelUsage[модель].contextWindow`, а CLI
  отдаёт для GPT значение этой переменной (замер 17.10.2026, CLI 2.1.280).
  Раньше знаменатель был `CONTEXT_WINDOW` → 160k. Чтобы запись нашлась и при
  суффиксе effort, понадобилась маленькая правка — §16.2.

## §16.2 Своя правка: окно контекста для GPT с суффиксом effort

- **Слой:** server · **Столкновение:** 🟡 (одна строка в апстримовской
  `readReportedContextWindow`, `claude-runtime.provider.ts`) · **PR:** нет
  (суффикс — специфика нашего шлюза).
- **Что нашли:** живой прогон через шлюз (`claude -p --model
  'gpt-6-astra(low)'`, CLI 2.1.280) вернул в `modelUsage` **две** записи:
  `claude-haiku-4-5-20251001` (служебный вызов самого CLI, 200k) и
  `gpt-6-astra(low)` (1M). А строки ассистента называют модель без суффикса
  (`gpt-6-astra`). Сопоставление апстрима снимает только `[1m]`, запасной
  вариант «одна запись в отчёте» не срабатывает из-за Haiku. В итоге при
  выбранном уровне effort счётчик откатывался на `CONTEXT_WINDOW` (160k), а с
  «Default» показывал 1M.
- **Фикс:** `withoutGatewayEffortSuffix` (рядом с `withGatewayEffortSuffix`
  в `claude-models.provider.ts`) снимает `(уровень)` у id на `gpt-`, а
  `readReportedContextWindow` применяет его к ключу после снятия `[1m]`.
- **Тест:** «a gateway GPT run with an effort suffix still finds its own
  window» в конце `claude-context-window.test.ts` (данные сняты с живого
  прогона). Контроль: без правки тест падает.
- **Мерж:** если апстрим перепишет сопоставление, проверить, что ключ
  `gpt-…(уровень)` по-прежнему находит свою запись при соседней Haiku.
