## Как читать таблицу

- **Слой** — где живёт правка (frontend / server / модель / инфра / UI).
- **Файлы** — ключевые точки, куда смотреть при мерже.
- **Столкновение с upstream** — насколько правка рискует конфликтовать при
  обновлении оригинала: 🟢 изолирована (свой файл/своя строка) · 🟡 правит общий
  upstream-файл (следить при мерже) · 🔴 глубоко переплетена с ядром.
- **PR в upstream** — предлагали/стоит ли предлагать к вливанию в оригинал.

## 3. Настройки пользователя в БД (per-user)

- **Слой:** server + frontend · **Столкновение:** 🟡/🔴 · **PR:** сильный кандидат.
- **Что:** upstream хранит UI/композер-настройки только в `localStorage` (теряются
  при чистке кэша, релогине, смене origin; не следуют за пользователем между
  устройствами). Форк зеркалит allowlist ключей `localStorage` в серверный blob
  `user_settings` (per-user): на входе — pull из БД в localStorage до чтения
  настроек приложением; на любое изменение — debounced push обратно в БД.
- **Файлы:**
  - БД: `server/modules/database/schema.ts` (таблица `user_settings`),
    `server/modules/database/repositories/user-settings.ts`.
  - API: `server/modules/settings/settings.{service,module,routes}.ts`
    (эндпоинты `GET/PUT /api/settings/user-settings`).
  - Frontend: `src/utils/userSettingsSync.js` (ядро синхро + автосинк),
    `src/components/auth/context/AuthContext.tsx` (запуск pull + автосинка),
    `src/utils/api.js` (`getUserSettings`/`updateUserSettings`).
- **Автосинк (важно):** push в БД идёт на **любое** изменение синхронизируемого
  ключа (`startUserSettingsAutoSync`: подписка на `ui-preferences:sync` + native
  `storage` + патч `localStorage.setItem`), а не только по кнопке «Сохранить».
  Guard `applyingServerSettings` гасит эхо при применении серверных настроек.
- **Что синхронизируется:** allowlist `SYNCED_SETTINGS_KEYS` в `userSettingsSync.js`
  (провайдер/модель/effort, язык, тема, `uiPreferences`, настройки редактора кода,
  режим дерева файлов, `starredProjects`, `permissionMode-*` по префиксу и др.).
- **Без секретов:** blob `user_settings` намеренно остаётся без секретов —
  репозиторий вырезает ключеподобные поля (`FORBIDDEN_KEYS`). Голосовой apiKey
  живёт в отдельной шифрованной таблице, см. §3-бис.
- **Мерж (v1.37.0):** upstream отрефакторил `server/routes/settings.js` в
  DI-модуль `server/modules/settings/*`; наши эндпоинты `user-settings` перенесены
  туда (service+module+routes) + тест `settings.service.test.ts`.

## 3-бис. Настройки голоса в БД + шифрование секретов (AES-256-GCM)

- **Слой:** server + frontend + БД · **Столкновение:** 🟡 · **PR:** кандидат
  (шифрование — сильный кандидат, апстриму его не хватает как примитива).
- **Симптом:** настройки Voice (STT/TTS) — URL, apiKey, модели, голос, формат —
  жили **только** в `localStorage`. Чистка кэша браузера стирала всю настройку,
  на новом устройстве всё вводилось заново.
- **Почему не решалось прежним механизмом:** §3 синхронизирует allowlist
  localStorage → `user_settings`, но `voiceConfig` туда сознательно не включали:
  в blob нельзя класть секреты, а **шифрования в проекте не было вообще**
  (`createCipheriv` не встречался ни разу). Таблица `user_credentials` тоже
  хранит значения открытым текстом — комментарий в схеме про «секреты живут
  здесь» описывал намерение, а не реальность (исправлен).
- **Что сделано:**
  1. **Примитив шифрования** — `server/shared/secret-box.ts`: AES-256-GCM,
     конверт `gcm.v1.<base64(iv|tag|ciphertext)>`. Мастер-ключ берётся из
     `CLOUDCLI_SECRET_KEY` (32 байта base64/hex) либо генерируется в
     `<каталог БД>/secret.key` с правами **0600**. Ключ лежит рядом с `auth.db`
     намеренно: шифротекст и ключ обязаны переезжать вместе, иначе смена
     `DATABASE_PATH` тихо осиротит все секреты.
  2. **Таблица `voice_settings`** (per-user) — `voice-settings.ts`. Поля
     `base_url/stt_model/tts_model/tts_voice/tts_format` открыто,
     `api_key_encrypted` — конверт. Обновление частичное и атомарное
     (транзакция): сохранение одного поля не стирает ключ.
  3. **API** — `GET/PUT /api/settings/voice-settings`. По умолчанию ответ несёт
     только `hasApiKey`; сырой ключ отдаётся **лишь** по явному
     `?revealApiKey=true`.
  4. **Клиент** — `useVoiceConfig` переписан на серверное хранилище с memory-кэшем
     (его читает `voiceApi` синхронно при сборке запроса), одноразовой миграцией
     старого `localStorage`-блоба наверх и сбросом кэша на выходе из аккаунта.
- **Граничный случай, определивший конструкцию:** когда задан свой `baseUrl`,
  браузер ходит в бэкенд голоса **напрямую** — серверный прокси намеренно
  игнорирует клиентские URL, чтобы не стать SSRF-плечом
  (`voice.module.ts`: «frontend-configured custom backends are called by the
  browser»). Поэтому для прямых вызовов ключ всё же нужен в браузере: он
  подтягивается лениво через `revealVoiceApiKey()` и живёт **только в памяти**,
  обратно в `localStorage` не пишется. На прокси-пути ключ не отправляется
  вовсе — сервер сам подставляет сохранённый (`parseVoiceOverrides`:
  заголовки в приоритете, БД — запасной вариант).
- **Модель угроз (честно):** защищает файл БД, а не хост. У кого доступ к
  `~/.cloudcli/`, у того и ключ, и база. Смысл в том, что apiKey перестал лежать
  открытым текстом в файле, который попадает в бэкапы, синхронизируется между
  машинами и передаётся при разборе проблем с БД.
- **Файлы:** `server/shared/secret-box.ts` (новый),
  `server/shared/tests/secret-box.test.ts` (новый, 8 тестов),
  `server/modules/database/repositories/voice-settings.ts` (новый),
  `server/modules/database/repositories/tests/voice-settings.test.ts` (новый,
  7 тестов на настоящей БД), `server/modules/database/{schema,migrations,index}.ts`,
  `server/modules/settings/settings.{service,module,routes}.ts`,
  `server/modules/voice/voice.{routes,module}.ts`,
  `src/hooks/useVoiceConfig.ts`, `src/lib/voiceApi.ts`, `src/utils/api.js`,
  `src/utils/userSettingsSync.js`, `src/components/auth/context/AuthContext.tsx`,
  `src/components/settings/view/tabs/VoiceSettingsTab.tsx`,
  `src/i18n/locales/en/settings.json`, `eslint.config.js` (secret-box в
  allowlist `backend-shared-utils` — иначе `boundaries/no-unknown`).
- **Заодно синхронизируются:** `quickSettingsHandlePosition` (позиция плавающей
  ручки) и `CLOUDCLI_HIDE_GITHUB_STAR` (скрытая плашка GitHub) — раньше
  терялись при чистке кэша. Полная сверка ключей `localStorage` показала, что
  других несинхронизируемых настроек не осталось.
- **Проверка:** 20/20 новых тестов, включая замер, что в колонке БД **нет**
  подстроки исходного ключа, а подделанный шифротекст не открывается.

### 4.4 Микрофон скрыт вне защищённого контекста (HTTPS/localhost)
- **Слой:** frontend · **Столкновение:** 🟢 · **PR:** кандидат (баг апстрима).
- **Симптом:** на телефоне по `http://100.64.0.27:3302` тап по микрофону падал с
  `Cannot read properties of undefined (reading 'getUserMedia')`.
- **Причина:** `navigator.mediaDevices` браузер отдаёт только в **secure context**
  (HTTPS либо localhost). Plain HTTP на Tailscale/LAN-IP таковым не является, и
  `navigator.mediaDevices` там `undefined`. Замер headless-Chrome по CDP на самом
  origin: `{origin:"http://100.64.0.27:3301", secure:false, md:"undefined",
  gum:"undefined"}`.
- **Апстрим болен тем же.** Проверено сравнением: `useVoiceInput.ts`,
  `useVoiceAvailable.ts`, `VoiceInputButton.tsx` и гейт в `ChatComposer.tsx`
  (строки 202/392) на момент v1.37.0 (`264e094`) **идентичны** нашим — гейт
  `useVoiceAvailable` апстримовский, не наш. Кнопка показывается по `voiceEnabled`
  + доступности бэкенда, **без** проверки самого API захвата.
- **Грабли диагностики:** «на 3301 микрофон есть, значит дело в форке» — ложный
  вывод. На 3301 крутится npm-пакет `@cloudcli-ai/cloudcli` **той же версии
  1.37.0** с той же строкой `mediaDevices.getUserMedia({audio:{echoCancellation:!0,
  noiseSuppression:!0}})`. Кнопка там видна, но нерабочая — по тапу та же ошибка.
  **Наличие иконки ≠ работающий микрофон.** Сравнивать инстансы нужно замером
  `isSecureContext`/`mediaDevices` на origin, а не наличием кнопки в UI.
- **Фикс:** (1) `useVoiceAvailable` дополнительно гейтит показ на `canCaptureMic()`
  (`typeof navigator.mediaDevices?.getUserMedia === 'function'`) — нет API захвата →
  кнопки нет (не ложное обещание). (2) `useVoiceInput.start` — fail-fast с понятным
  текстом «Microphone needs a secure connection (HTTPS or localhost).», если запись

### 4.7 Автозаголовок срабатывает и для новых сеансов (гонка индексации)

### 4.8 Промт заголовка — универсальный, срабатывает на любом запросе
- **Слой:** backend · **Столкновение:** 🟢 · **PR:** вместе с 4.6.
- **Симптом:** заголовок генерировался «через раз». Часть сеансов получала
  короткое имя, часть навсегда оставалась с обрезанным сырым запросом — при
  исправном сервисе и работающей кнопке перегенерации.
- **Причина — невыполнимое требование в промте.** Было жёстко: «Первые два
  слова **обязаны** называть предмет: проект, домен, сервис, номер задачи или
  файл». Если в первом запросе ничего этого нет (надиктованный голосом вопрос,
  обсуждение без привязки к задаче), модель упирается в требование, которое
  физически не может выполнить, и вместо заголовка отвечает пояснением. Дальше
  срабатывает отбраковка в `sanitizeModelTitle` (ответ длиннее `MAX_TITLE_LENGTH
  * 2` → `null`), и имя откатывается на сырой запрос. Отказ выглядел как «фича
  не работает», хотя запрос к модели проходил успешно.
- **Фикс:** требование к предмету стало **приоритетным списком**, а не
  обязанностью: (1) проект/домен/репозиторий/файл/номер задачи, если назван;
  (2) иначе — главная тема запроса. Добавлены: явное «заголовок обязателен
  всегда, не отказывайся и не проси уточнений»; разрешение обойтись без тире,
  когда действие не выражено; указание игнорировать оговорки и самоперебивания
  надиктованного текста.
- **Границы:** порог `MAX_TITLE_LENGTH` (48) не трогали — запросы короче него

### 4.9 Автозаголовок: источник — первое сообщение, а не имя из истории
- **Слой:** backend + frontend · **Столкновение:** 🟡 · **PR:** вместе с 4.6.
- **Симптом:** автоматическое переименование «то работает, то нет». Ручная
  кнопка на десктопе отрабатывала, автоматика — почти никогда. На мобиле

- **Фикс 2:** источником стал `extractFirstUserPrompt` (первое сообщение);

  раньше он был только в десктопном меню, хотя все нужные пропсы

### 4.10 Автоархив служебных сеансов (security-review)
- **Слой:** backend + БД · **Столкновение:** 🟡 · **PR:** кандидат.
- **Симптом:** плагин security-review открывает сеанс на каждый коммит (иногда
  два), и его прогоны хоронят настоящие разговоры. Замер на рабочей БД:
  **907 из 2043** активных сеансов — служебные.
- **Решение:** переиспользуем **существующий** механизм архива апстрима
  (`isArchived` + раздел «Архив» в сайдбаре) вместо новой сущности. При
  индексации служебный сеанс сразу помечается архивным, поэтому в общем списке
  не появляется, но остаётся доступным и находимым в архиве. Новых экранов,
  таблиц и настроек не добавлено — это и был критерий выбора (минимум
  расхождений с оригиналом).
- **Как отличаем (важно — не по названию).** Заголовки служебных сеансов пишет
  та же модель, и читаются они как обычная работа («kb-switch.sh — проверка
  уязвимостей»), поэтому правило по имени пряло бы и живые чаты. Признак —
  пара «SDK-entrypoint + шаблонная первая строка промта»:
  `entrypoint === 'sdk-py'` (CloudCLI представляется `sdk-ts`, то есть чаты из
  самого приложения под правило не попадают ни при каком содержимом) **и**
  первый пользовательский ход начинается с `Review this change for security
  vulnerabilities` либо `You previously flagged these candidate
  vulnerabilities`. Замер по всей БД: **907 из 907** служебных распознаны,
  ложных срабатываний среди остальных 260 — **ноль**.
- **Ключевая тонкость — переиндексация.** `createSession` штатно снимает
  архивный флаг при каждой записи в транскрипт («сеанс ожил»), а плагин пишет в
  свои сеансы постоянно → все ревью возвращались бы в сайдбар. Правку пришлось
  внести в **обе** ветки записи: `UPDATE` для найденного
  `provider_session_id` и `ON CONFLICT` — их две, и первая срабатывает раньше
  (поймано тестом, не глазами).
- **Побочная экономия:** для архивных сеансов не запускается генерация
  заголовка — их «промт» это ~20 КБ машинного JSON, платить за это незачем.
- **Ручное решение пользователя уважается:** флаг форсится только при `true`;

### 4.13 Диктовка отвечает быстрее: timeslice + прогрев соединения

- **Слой:** frontend · **Столкновение:** 🟡 (общий `useVoiceInput`) · **PR:**
  кандидат (полезно любому пользователю удалённого STT).
- **Симптом:** через микрофон CloudCLI текст появлялся заметно позже, чем через
  нативный клиент diktor на той же машине и с тем же сервером.
- **Что оказалось НЕ причиной** (проверено замерами, чтобы не искали заново):
  - **не формат.** Гипотеза «webm медленнее сырого PCM» опровергнута: то же
    30-секундное аудио на боевой сервер — PCM 960 КБ → 1.17/1.14 с, webm 112 КБ
    → 1.00/1.08 с. **WebM даже быстрее**, а весит в 8.6 раза меньше — с телефона
    это решающе. Декод webm через PyAV на сервере — ~80 мс на 30 с звука.
    **Менять формат на PCM не надо, это ухудшит.**
  - **не LLM-полировка.** Путь CloudCLI идёт без `window_class`, профиль не
    подбирается, шаг пропускается; прогон с `no_polish=1` дал то же время.
- **Настоящая причина — три задержки на стороне браузера**, все ПОСЛЕ того как
  пользователь отпустил кнопку (нативный клиент не платит ни одной):
  1. **кодирование Opus одним куском.** `rec.start()` вызывался без `timeslice`,
     поэтому браузер финализировал контейнер только на `stop()` — цена росла с
     длиной надиктовки;
  2. **TLS-хендшейк** ~280 мс на новое соединение;
  3. **CORS-preflight** ~376 мс (`OPTIONS`), которого у нативного клиента нет
     как класса.
- **Как чиним:**
  - `rec.start(RECORDER_TIMESLICE_MS)` (1000 мс) — Opus кодируется по ходу
    записи, на `stop()` дописывается только последний чанк. Чанков теперь много,
    но склейка в один `Blob` и порог «слишком короткой записи» (800 байт)
    считаются по итоговому размеру, поэтому логика не изменилась;
  - `warmUpVoiceBackend()` дёргает `/health` в момент **нажатия** на микрофон:
    пока человек говорит, TLS и preflight успевают пройти фоном. Вызов
    «выстрелил и забыл», любая ошибка гасится — это оптимизация, ронять из-за
    неё диктовку нельзя. Греется только прямой путь (когда задан свой
    `baseUrl`); через прокси CloudCLI соединение и так живое.
- **Третья часть — на стороне diktor, не здесь:** `access-control-max-age` 600
  → 86400, чтобы preflight не повторялся каждые 10 минут (репозиторий diktor,
  ветка `dev`).
- **Файлы:** `src/modules/chat/hooks/useVoiceInput.ts`, `src/shared/api.ts`.

## 7. Сессия не сбрасывается при обновлении страницы (регресс v1.37.2)

- **Слой:** backend + frontend · **Столкновение:** 🔴 (ядро авторизации) ·
  **PR:** да, кандидат — это баг апстрима, не наша специфика.
- **Симптом:** после релиза 1.37.2 при **каждом** обновлении страницы
  запрашивались логин и пароль.
- **Источник:** upstream-коммит `0a2ad343` («improve chat view and resolve
  bandwidth issue», #1153), который принёс авто-refresh токена и заголовок
  `X-Auth-Error`. Срок жизни токена (7 дней) **ни при чём** — токен был валиден,
  клиент выбрасывал его сам.
- **Причина 1 (главная).** В `checkAuthStatus` любой неуспешный ответ
  `GET /api/auth/user` вызывал `clearSession()`. Не только 401, но и 5xx, ошибка
  прокси или запрос, попавший в момент рестарта systemd-юнита. Токен при этом
  полностью рабочий.
- **Причина 2 (усиливающая).** В `authenticatedFetch` (и в XHR-загрузке файлов)
  `expireAuthSession()` вызывался на **сам факт** наличия заголовка
  `X-Auth-Error`, без проверки статуса. А сервер ставит этот заголовок в том
  числе когда токен вообще **не был прислан** (`middleware/auth.js`: ветка
  «нет токена» → `invalid-token`). Любой запрос, ушедший до того, как React
  прочитал localStorage, стирал валидную сессию.
- **Фикс:**
  - `AuthContext.checkAuthStatus` — `clearSession()` только при `status === 401`;
    сетевые и 5xx-ошибки сессию не трогают, ответ 200 без тела пользователя —
    тоже (это некорректный ответ, а не вердикт о токене);
  - `authenticatedFetch` и `useFileTreeUpload` — `expireAuthSession()` только
    при связке «токен отправляли **и** `status === 401` **и** заголовок есть»;
  - срок токена `7d` → **365d** (`TOKEN_TTL`), переопределяется переменной
    окружения `CLOUDCLI_SESSION_TTL`. Вместе с уже существующим авто-refresh
    (обновление после половины срока, при фокусе/возврате вкладки) сессия
    становится практически бессрочной.
- **Почему не «вечно» буквально:** у форка нет списка отзыва токенов, поэтому
  токен без срока годности нельзя аннулировать вообще никак при потере
  устройства. 365 дней + автопродление даёт тот же практический эффект,
  сохраняя возможность истечения. Решение согласовано с CEO.
- **Файлы:** `server/modules/auth/auth.middleware.ts`,
  `src/components/auth/context/AuthContext.tsx`, `src/utils/api.js`,
  `src/components/file-tree/hooks/useFileTreeUpload.ts`.
- **Риск при мерже:** 🔴 — все четыре файла активно правит upstream. При
  обновлении проверять, не вернулись ли безусловные `clearSession()` /
  `expireAuthSession()`.

## 10. Бесконечное мигание splash ↔ «Загрузка CloudCLI» (побочный эффект 365-дневного токена)

- **Слой:** frontend · **Столкновение:** 🔴 (ядро авторизации) ·
  **PR:** да, кандидат — баг воспроизводится и на апстриме, наш TTL лишь ускорил
  его наступление.
- **Симптом:** после нескольких часов простоя (или при заходе по прямой ссылке
  `/session/<id>`) страница бесконечно перепрыгивает между splash-экраном
  «CloudCLI» и экраном «Загрузка CloudCLI / Настройка рабочего пространства».
  Браузер при этом считает страницу загруженной. Чистка кук не помогает —
  токен лежит в `localStorage`. Помогает стереть путь сессии из адресной строки.
- **Причина (цикл из трёх звеньев):**
  1. Сервер в `authenticateToken` ставит заголовок `X-Refreshed-Token` на
     **каждый** аутентифицированный ответ, как только токен прошёл половину
     срока жизни (`auth.middleware.ts:73-80`).
  2. `authenticatedFetch` безусловно клала полученный токен через
     `storeAuthToken`, а та безусловно поднимала событие
     `auth-token-refreshed` — даже когда значение не изменилось.
  3. `AuthContext` по этому событию делал `setToken(...)`; `token` был в
     зависимостях `checkAuthStatus`, а тот — в зависимостях эффекта
     инициализации. Новый `token` → новая ссылка колбэка → повторный запуск
     стартовой проверки → `setIsLoading(true)` → splash → новый запрос →
     снова заголовок. Петля самоподдерживающаяся.
- **Почему проявилось только сейчас:** заголовок появляется после половины
  срока жизни токена. При апстримных 7 днях это ~3.5 дня, при наших 365 —
  ~183 дня (см. секцию 7). Токен пересёк экватор, и заголовок стал приходить
  на каждый запрос.
- **Почему хуже на `/session/<id>`:** резолвер сессии в `useProjectsState`
  дополнительно дёргал `api.sessionDetails`, и каждый такой запрос подстёгивал
  цикл. На `/` эффект выходит сразу по `if (!sessionId) return`.
- **Фикс (четыре точки):**
  - `src/shared/authToken.ts` — `storeAuthToken` сравнивает новый токен с уже
    сохранённым и поднимает событие **только при реальной ротации**. Это
    корневая правка: она разрывает петлю у источника;
  - `src/modules/auth/context/AuthContext.tsx` — `checkAuthStatus` читает токен
    через `tokenRef`, `token` убран из зависимостей. Ротация токена больше не
    перезапускает стартовую проверку;
  - там же — `setIsLoading(true)` только когда пользователь ещё не загружен
    (`userRef.current`). Повторная проверка не роняет рабочую область на splash;
  - `src/modules/project-workspace/hooks/useProjectsState.ts` — `selectedProject`
    читается через `selectedProjectRef` и снят с зависимостей резолвера сессии,
    чтобы выбор проекта не перезапускал lookup.
- **Тесты:** `src/shared/tests/authToken.test.ts` — «re-storing the same token
  does not announce a refresh».
- **Файлы:** `src/shared/authToken.ts`,
  `src/modules/auth/context/AuthContext.tsx`,
  `src/modules/project-workspace/hooks/useProjectsState.ts`.
- **Риск при мерже:** 🔴 — все три файла активно правит upstream. При обновлении
  проверять, не вернулось ли безусловное `dispatchEvent` в `storeAuthToken` и
  не появился ли снова `token` в зависимостях `checkAuthStatus`.

## 11. Раздача форка команде: GitHub-зеркало + скрипт обновления

- **Слой:** инфраструктура · **Столкновение:** 🟢 (новые файлы) · **PR:** нет
  (специфика холдинга, апстриму не нужно).
- **Зачем:** форком пользуется не только Артём. Раньше коллегам уходил
  zip-архив — без истории, без внятного способа обновиться. Теперь у них
  нормальный git-репозиторий и обновление одной командой.
- **Схема зеркала:** внутренний git холдинга (`goldjaxe`,
  `git.q-standard.com`) остаётся **основным** — разработка идёт там, в ветке
  `feat/goldjaxe-improvements`. GitHub `elchako/cloudcli-fork` (приватный) —
  **зеркало только на чтение** для команды, ветка `main`:

  ```
  Артём → goldjaxe/feat/goldjaxe-improvements   (основной, сюда коммиты)
            ↓ git push github …:main
          github/main                            (зеркало, отсюда тянет команда)
  ```

  Публикация новой версии:
  `git push github feat/goldjaxe-improvements:main`.
  Есть алиас: `git publish` (см. ниже).
- **Почему зеркало односторонне:** команда в GitHub не пушит. Если кто-то
  закоммитит туда, ветки разойдутся и `update.sh` остановится на
  `merge --ff-only`, а не устроит молчаливый merge-коммит.
- **Скрипт обновления:** `scripts/update.sh` — fetch → показ новых коммитов →
  `merge --ff-only` → `npm install --include=dev` → `npm run build` →
  перезапуск службы. Режимы `--check` (только посмотреть) и `--no-restart`.
  Обёртка: `npm run update`.
- **Системы у всех разные,** поэтому способ перезапуска не захардкожен:
  автоопределение (systemd user-scope → pm2 → launchd), поверх — локальный
  конфиг `scripts/update.local.conf` (в `.gitignore`, у каждой машины свой) с
  `CLOUDCLI_SERVICE` / `CLOUDCLI_SERVICE_SCOPE` / `CLOUDCLI_LAUNCHD_LABEL` /
  `CLOUDCLI_RESTART_CMD`. Не нашлось способа — скрипт не угадывает, а
  печатает подсказку и выходит с ошибкой; код при этом уже собран.
- **Защиты в скрипте:** отказ при незакоммиченных правках (иначе `merge` их
  затрёт), проверка Node ≥ 22, отказ на detached HEAD, `--include=dev` при
  установке (при `NODE_ENV=production` npm иначе пропустит devDependencies и
  сборка упадёт на `vite: not found`).
- **Файлы:** `scripts/update.sh`, `scripts/update.local.conf.example`,
  `docs/ru/install.md` (установка с нуля + обновление + типовые проблемы),
  `.gitignore` (+`scripts/update.local.conf`), `package.json`
  (+скрипт `update`).
- **Риск при мерже:** 🟢 — всё новое и своё. Единственная общая точка —
  `package.json` (секция `scripts`) и `.gitignore`; конфликт, если возникнет,
  разрешается тривиально (обе стороны дописывают строки).
- **Что проверить перед раздачей людям:** репозиторий на GitHub приватный;
  в истории нет секретов (`.env`, `*.db` — в `.gitignore` с самого начала);
  из чувствительного в доках только Tailscale-IP `100.64.0.27` (CGNAT,
  доступен лишь внутри tailnet).

## 12. Живые заголовки везде, актуальный пуш, однострочная мобильная шапка и догоняющий автоархив

### 12.1 Заголовок открытого чата и tooltip обновляются в момент переименования

- **Слой:** server + frontend · **Столкновение:** 🟡 (общий wire-формат
  `session_upserted` и обработчик в `useProjectsState`) · **PR:** кандидат.
- **Симптом:** ИИ-переименование обновляло только строку в сайдбаре. Заголовок
  **открытого** чата (шапка + title вкладки браузера) менялся лишь после
  перезагрузки страницы или ухода в другой чат и обратно, а tooltip на
  десктопе показывал только короткую тему без исходного запроса — до ручной
  регенерации, которая возвращала `fullTitle` в REST-ответе.
- **Причина:** событие `session_upserted` не несло `fullTitle`, обработчик на
  клиенте трогал `selectedSession` только при смене алиаса
  (provider-id → app-id), а `scheduleTitle` в синхронизаторе писал заголовок в
  БД молча — live-обновление сайдбара случайно работало лишь потому, что ран
  продолжал писать транскрипт и watcher слал очередной дельта-апдейт.
- **Решение:** (1) `SessionUpsertedEvent.session` дополнен полем
  `fullTitle` (string|null — истина БД, включая явный null после ручного
  rename); (2) `scheduleTitle`, `renameSessionById` и
  `regenerateSessionTitleById` сразу рассылают `broadcastSessionUpserted` —
  второй клиент (телефон/десктоп) видит смену имени мгновенно;
  (3) обработчик в `useProjectsState` точечно мержит `summary`/`fullTitle`/
  `lastActivity` в `selectedSession` по совпадению любого из alias-id —
  спред всего payload'а нарочно не используем: он бы затирал живой
  `messageCount` нулём из события. Пустой `summary` в событии заголовок не
  обнуляет (та же защита, что в сайдбаре); отсутствующий ключ `fullTitle`
  (оптимистичная регистрация) не затирает известное значение, а явный null
  затирает — это правда после ручного rename.
- **Ловушка при реализации:** статический импорт broadcast-сервиса из
  синхронизатора замкнул цикл модулей (synchronizer → broadcast → projects →
  provider registry → synchronizer) и уронил инициализацию провайдеров
  (TDZ, `Cannot access 'ClaudeSessionSynchronizer' before initialization`) —
  поймано тестом архивации, лечится ленивым `await import()` внутри
  `scheduleTitle` с поясняющим комментарием.
- **Файлы:** `server/shared/types.ts`,
  `server/modules/websocket/services/session-upsert-broadcast.service.ts`,
  `server/modules/providers/list/claude/claude-session-synchronizer.provider.ts`,
  `server/modules/providers/services/sessions.service.ts`,
  `src/modules/project-workspace/hooks/useProjectsState.ts`; тест
  `src/modules/project-workspace/tests/projectsStateSelectedTitle.test.ts` (3).

### 12.2 Push-уведомление называет сессию актуальным именем

- **Слой:** server · **Столкновение:** 🟡 (общий файл уведомлений) ·

- **Симптом:** пуш о завершении рана приходил со старым названием сессии

- **Причина:** `resolveSessionName` в оркестраторе уведомлений безоговорочно

### 12.4 Догоняющий автоархив служебных сеансов при старте + потоковый детектор

- **Слой:** server · **Столкновение:** 🟡 (свой сервис, общие вызовы в
  watcher) · **PR:** часть кандидата 4.10.
- **Симптом:** часть security-review сеансов оставалась видимой и в
  «Разговорах», и внутри проектов, хотя детектор 4.10 их распознавал.
- **Причина:** автоархив 4.10 срабатывает только при (пере)индексации файла,
  а курсор сканирования (`scan_state.last_scanned_at`) движется только
  вперёд — сеансы, проиндексированные старым билдом без фичи (или за
  миллисекунды до появления первой строки промта на диске), никогда не
  переоцениваются. Проверено на боевой БД: транскрипты проскочивших сеансов
  правилу соответствуют (`sdk-py` + маркер), детектор на них `true`.
- **Решение:** `archiveAutomatedSessions()` — идемпотентная sweep-зачистка:
  все незаархивированные Claude-строки с `jsonl_path` перепроверяются
  детектором, совпадения уходят в архив. Запускается fire-and-forget при
  старте watcher'а на каждом boot — заодно это страховка от гонки
  «файл проиндексирован раньше первой строки». Последовательный обход
  нарочно: фоновая задача не должна устраивать тысячу конкурентных чтений.
  Разовый скрипт 4.10 (`scripts/archive-automated-sessions.mjs`) остаётся
  для ручного прогона.
- **Заодно:** детектор переведён с полного чтения файла на потоковое
  построчное (readline + ранний выход, потолок 8 МБ) — раньше каждый
  синк и sweep читали транскрипты целиком (десятки МБ у длинных сеансов)
  ради вердикта по третьей строке. Семантика вердиктов не изменилась
  (первый содержательный user-ход решает; битый файл → не automated).
- **Файлы:** `server/modules/providers/services/automated-session.service.ts`
  (sweep + потоковый детектор),
  `server/modules/database/repositories/sessions.db.ts`
  (`getUnarchivedSessionsWithTranscriptPath`),
  `server/modules/providers/services/sessions-watcher.service.ts` (запуск);
  тест `automated-session-sweep.test.ts` (архивит plugin-сеанс, не трогает
  живой чат и битый путь, идемпотентен).
